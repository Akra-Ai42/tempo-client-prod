Vision du projet

Tempo Client V2 est un outil décisionnel pour conseillers bancaires qui combine :

  • Un modèle ML qui prédit la probabilité qu'un client parte (churn)
  • Une couche d'explication qui transforme les SHAP values en langage naturel via LLM
  • Un système d'alertes et de recommandations d'actions
  • Un dashboard direction avec les KPI business et ML Ops

Spécificité pédagogique : trois incidents volontaires sont injectés dans le code pour servir d'exercice aux étudiants Devoteam MSc1 Finance/Assurance.

Étape 1. Je me connecte

Scénario : Marie Dubois ouvre son navigateur sur Tempo Client
  1. Le navigateur charge /static/shared/login.html → formulaire HTML sobre, champs username et password
  2. Marie saisit conseiller_lille et son mot de passe, clique "Se connecter"
  3. login.js envoie un POST /auth/login avec payload JSON → credentials: 'same-origin' pour que le cookie soit géré
  4. Côté serveur, app/auth/routes.py reçoit la requête → verify_password() compare avec le hash bcrypt stocké → si user inexistant : bcrypt bidon pour éviter la timing attack, puis False → si password incorrect : retourne False → si tout OK : retourne l'objet User
  5. login_user() crée la session Starlette signée dans le cookie → SessionMiddleware encode et signe, durée 24h
  6. Réponse HTTP 200 avec le cookie Set-Cookie: session=... et body JSON
  7. login.js lit info.role et redirige vers le dashboard adapté
↓
Marie arrive sur son dashboard. Le cookie est posé. Les prochaines requêtes l'enverront automatiquement.

Détails techniques clés

  • Hash bcrypt rounds=12 : vérification en environ 100 ms, défense native brute-force
  • Message d'erreur générique "Identifiants invalides" : défense contre énumération
  • Cookie signé, pas chiffré : le serveur vérifie l'intégrité
  • Pattern Dependency Injection : chaque endpoint protégé déclare Depends(get_current_user)

Étape 5. Je consulte les actions recommandées

Scénario : la checklist des actions à mener se remplit

  3. Construction du contexte features (les 7 features ML du client)
  4. Appel recommend_actions(features, churn_score) : → pour chaque règle, évalue la condition Python dans contexte restreint → eval(condition, {"__builtins__": {}}, context) → exceptions silencieuses : règle non évaluable = False + warning → filtre et trie par priorité : haute > moyenne > basse → prend les 3 premières

↓

Tip. eval restreint

Les règles ne viennent pas d'input utilisateur. Elles sont écrites par le data scientist, sérialisées dans un pkl contrôlé. __builtins__ vide = pas d'accès à l'environnement. Sécurité par le périmètre, pas par la syntaxe.

Infra B. Chaque appel LLM

Scénario : un endpoint appelle explain_service.explain_score(...)
  1. Construction cache key : hash(client_id, features, model)
  2. Lookup dans TTLCache interne : → cache HIT : retour en 5 ms, 0 appel réseau, 0 USD → cache MISS : continuer
  3. Prompt système environ 150 tokens (role banking, français, concis)
  4. Prompt user : nom, prénom, score, features en bullet points
  5. Appel provider.complete(...) : → singleton httpx.AsyncClient partagé → POST OpenRouter avec headers Authorization + Referer + Title → retry 3x avec backoff 1-2-4s sur 429 et 5xx → timeout 30 secondes
  6. OpenRouter route vers Llama 70B : environ 2-3 secondes, 50 à 150 tokens output
  7. Retour LLMResponse avec coût calculé via dict pricing.py
  8. log_llm_call() écrit JSONL : ts, model, tokens, cost_usd, latency_ms
  9. Mise en cache de la réponse avec TTL 86400 s
↓
Le prochain appel pour le même client sera un HIT. 0 réseau. 0 USD. 5 ms. Même qualité.

Infra C. Chaque requête RBAC

Scénario : un endpoint protégé reçoit une requête
  1. FastAPI résout la dépendance Depends(get_current_user)
  2. get_current_user() lit request.session.get("username") → si None : HTTPException 401 "Non authentifie" → si présent : récupère l'User
  3. Si endpoint utilise Depends(require_direction) : → vérifie user.role == "direction" sinon 403
  4. Pour un endpoint listing comme /clients/mine : → filter_clients_by_user applique le filtre régional → cette ligne portera l'incident 3 (semaine 4)
  5. Pour un endpoint ressource comme /score/{id} : → vérification explicite region du client vs region user → 403 si incompatible, défense en profondeur
↓
Le RBAC fonctionne en 2 couches : filtre pour les listings, vérification explicite pour les ressources individuelles.

Infra D. Vue agrégée direction, pattern lecture pure

Scénario : la direction demande le dashboard global
  1. GET /dashboard/direction arrive avec cookie session direction
  2. FastAPI résout Depends(require_direction) → vérifie user.role == "direction" sinon 403
  3. Le endpoint est purement orchestrateur : → aucun appel ML, LLM, base de données → compose 3 sources déjà en mémoire ou sur disque
  4. Source 1 : scores pré-calculés en mémoire via get_all_scores()
  5. Source 2 : log coût LLM sur disque via read_cost_log(since=first_of_month) et read_cost_log(since=24h_ago)
  6. Source 3 : clients en mémoire via get_all_clients(), indexé par id O(1)

  8. Retour : DashboardKPI Pydantic validé automatiquement

Le endpoint renvoie en ~1 ms sur 1000 clients. Zéro I/O base, zéro inférence, zéro appel réseau. Juste de la composition de données déjà payées au boot.
Tip. Pattern vue agrégée pure

Composition sans mutation, sans effet de bord. Si demain on migre llm_cost_log.jsonl vers Postgres, on change uniquement read_cost_log(). routes.py et app.js ne bougent pas. C'est ça l'archi hexagonale appliquée à l'IA.

Tip. Trade-off scalabilité assumé

Si le portefeuille passe à 1M clients, get_all_scores() ne tient plus en mémoire. C'est à ce moment-là qu'on introduit une base, pas avant. Simplicité maintenant, migration en 2027 si besoin.

Infra E. Monitoring Evidently, adapter branché à chaud

Scénario : la dérive des données est calculée et exposée

  7. Chaque GET /dashboard/direction lit ce cache (instantané)

↓
Le monitoring tourne automatiquement au boot et à la demande. 3 features dérivées visibles dès le premier chargement. Le rapport HTML complet est consultable en 1 clic.

drift.py ne connaît ni le dashboard ni les endpoints. Si on remplace Evidently par Nannyml ou Alibi Detect, on change uniquement ce fichier.

Tip. Un adapter, deux consommateurs

Tip. Singleton httpx

Chaque httpx.AsyncClient() ouvre un pool. Un singleton réutilise la connexion TCP, environ 50 ms économisés par appel. Sur 1000 appels par jour : 50 secondes économisées quotidiennement.

Tip. Retry seulement sur 429 et 5xx

4xx hors 429 = erreur client, retry inutile. 429 = rate limit. 5xx = serveur. Règle d'or : jamais retry une erreur dont la cause ne va pas disparaître.

Brique 3. Dataset + XGBoost + SHAP Livrée 20/10/2026

Objectif

Construire la fondation ML : dataset synthétique de 1000 clients, XGBoost de scoring, SHAP explainer.

Comprendre XGBoost, SHAP et LLM

  • XGBoost (le devin) : donne un score 0.0 à 1.0. Boîte noire.
  • SHAP (le détective) : N'EST PAS un modèle ML, algorithme mathématique qui analyse XGBoost. Preuve : pas de .fit().
  • LLM (le traducteur) : transforme les shap_values en français lisible. Ne calcule rien.

En une phrase : XGBoost dit COMBIEN, SHAP dit POURQUOI, LLM dit COMMENT l'expliquer.

Métriques réelles

Glossaire technique

  • AUC-ROC : capacité à distinguer 2 classes. > 0.9 excellent.
  • bcrypt : hash volontairement lent (~100 ms). Standard depuis 1999.
  • Cache LRU : quand plein, vire l'entrée pas utilisée depuis le plus longtemps.
  • Dependency Injection : FastAPI injecte via Depends().
  • Lazy loading : calculer à la demande. Opposé du pré-scoring.
  • Pré-scoring : calculer tous les scores au démarrage. Boot plus lent, requêtes rapides.
  • RBAC : Role-Based Access Control.
  • SessionMiddleware : middleware Starlette pour cookies session signés.
  • SHAP : méthode mathématique pour attribuer à chaque feature sa contribution. Pas un modèle ML.
  • Singleton : une seule instance partagée.
  • Timing attack : attaque exploitant les temps de réponse.
  • TreeExplainer : SHAP optimisé pour modèles arbres. 1000x plus rapide.
  • TTL : durée de vie d'une entrée en cache.
  • XGBoost : algorithme d'arbres gradient-boosted. Standard tabulaire.
